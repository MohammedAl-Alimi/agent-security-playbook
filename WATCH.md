# 🔭 AI Security Watch

A daily-updated log of new vulnerabilities, breaches, and research affecting AI-generated ("vibe-coded") applications. Maintained by a scheduled Claude cloud agent; every entry is verified against a primary source before it lands here.

**Last checked:** 2026-09-20 — check in progress.

---

## How this file is updated

- A cloud agent runs once a day. It searches for incidents, CVEs, and research from the last few days that affect AI-generated apps (missing auth/RLS, leaked secrets, supply-chain attacks, prompt injection, framework CVEs).
- New, verified findings are **appended** to the log below, each with a source URL.
- A finding that should change one of the [rule chapters](rules/) is flagged with **⚠ PROPOSED RULE UPDATE** and the chapter number, for human review — the agent never edits the chapters itself.
- If nothing new and verifiable turns up, only the **Last checked** line above is updated.
- The routine that maintains this file follows the [Agent Routines Playbook](https://github.com/MohammedAl-Alimi/agent-routines-playbook) (security-advisory-watch recipe).

### 2026-08-20

- **isolated-vm sandbox escape (GHSA-864f-rcv7-6rh4):** A critical type-confusion bug in `ExternalCopy`'s `transferList` handling lets untrusted JavaScript running inside an isolate corrupt host memory for a full guest-to-host escape; all versions ≤ 7.0.0 are affected, patched in 6.2.0 and 7.0.1. Matters for AI-built apps because agent frameworks and code-execution tools commonly run model-generated or user-supplied JS inside isolated-vm, so an escape turns that sandbox into host RCE. [Endor Labs advisory](https://www.endorlabs.com/learn/ghsa-864f-rcv7-6rh4-critical-type-confusion-vulnerability-in-isolated-vm)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): note that JS sandboxes used to run LLM/agent-generated code (e.g. isolated-vm) are escapable and must be patched and treated as defense-in-depth, not a trust boundary.
- **@logto/tunnel path traversal (CVE-2026-63188):** The Logto CLI tunnel serves custom sign-in experience assets from `--experience-path`, but `../` segments in a static-asset request let an unauthenticated requester read files outside that directory that the CLI process can read (High, CVSS 8.7); fixed in 0.3.9. Matters for AI-built apps that wire up Logto for authentication and run the dev tunnel, since it can leak local files (including secrets) while reachable. [GitLab advisory (CVE-2026-63188)](https://advisories.gitlab.com/npm/@logto/tunnel/CVE-2026-63188/)
  - ⚠ PROPOSED RULE UPDATE (chapter 03): reinforce that any static-file endpoint must normalize and reject `../` traversal before resolving a path, including in dev/CLI tooling that serves assets.

### 2026-08-21

- **@ai-sdk/harness-cline sandbox path traversal (GHSA-222v-gj5h-ff73):** The Cline harness's file tools (read, write, edit, grep, glob, ls) failed to restrict access to the session working directory and had insufficient symlink restrictions, letting a manipulated request reach files outside the sandbox, including other sessions' files (High, CVSS 7.7); affects `@ai-sdk/harness-cline` ≤ 1.0.7, fixed in 1.0.8. Matters for AI-built apps because a prompt-injected or manipulated agent could read another session's env vars, credentials, and config, or corrupt files across workspace boundaries in allow-edits mode. [GitHub advisory GHSA-222v-gj5h-ff73](https://github.com/vercel/ai/security/advisories/GHSA-222v-gj5h-ff73)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): note that agent-harness file tools must canonicalize/resolve real paths and reject symlink escapes before touching the filesystem, not just check the input path string.
- **@ai-sdk/harness-opencode unauthenticated loopback control API (GHSA-vmqp-7rwf-cq3w):** The OpenCode harness's loopback HTTP control server starts with no authentication, so untrusted code running in the same sandbox can call the control API to inject prompts into the active session and make the host HarnessAgent execute attacker-chosen host tools (Moderate, CVSS 6.3); affects `@ai-sdk/harness-opencode` ≤ 1.0.72, fixed in 1.0.73. Matters for AI-built apps using this harness with host-provided tools and the default non-interactive approval policy, since it can turn sandboxed code execution into unauthorized secret lookups, deployments, or cloud API calls. [GitHub advisory GHSA-vmqp-7rwf-cq3w](https://github.com/vercel/ai/security/advisories/GHSA-vmqp-7rwf-cq3w)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): require that any loopback/local control API exposed by an agent harness be authenticated, not just network-local, since sandboxed/untrusted code shares that network namespace.

### 2026-08-25

- **Trojanized npm "streak"/date-utility packages drop RedC2 4.0 Linux backdoor:** TrendAI Research identified ~14 npm packages posing as calendar/streak-tracking date-math utilities (names including `streak-metrics-math`, `streak-map-cache`, `streak-map-kit`, `streak-calc-math`) that ship a genuine, working library alongside a bundled Linux ELF binary; importing the package (even transitively, no install hook needed) launches the binary as a detached background process, installing the "RedShell" beacon for the RedC2 4.0 C2 framework, which steals SSH keys/browser credentials, persists via cron/shell-startup/user services, and pivots network traffic. Matters for AI-built apps because coding agents frequently auto-add small utility packages like these to satisfy a feature request without a human reviewing the dependency, and a single transitive import is enough to get backdoored on `npm install` with no build step required to trigger it. [TrendAI Research: "Prompting the Payload" — RedC2 AI-powered Linux implant](https://www.trendaisecurity.com/en-us/resources-insights/trendai-security-blog/redc2-ai-powered-linux-implant)
  - ⚠ PROPOSED RULE UPDATE (chapter 14): recommend auditing new/unfamiliar npm dependencies (especially ones an agent added on its own) against known-malicious-package feeds before install, not just after a CVE is filed, since malware-laced packages like this one predate any GHSA/CVE entry.
- **JSONata arbitrary code execution via crafted expressions (GHSA-66mm-25pp-rfff, GHSA-2943-5xfg-gq5f, GHSA-8gq3-vp5j-2grp / CVE-2026-77413, -77414, -77415):** Three critical sandbox-escape bugs in the `jsonata` npm package (prototype-pollution style tricks with `$hasOwnProperty`/`$spread`/`$constructor`, an overwritable `$clone`, and an `applyProcedure` misuse of `proc.arguments.forEach`) let a crafted JSONata expression reach `process.getBuiltinModule('child_process')` and run arbitrary code with the host process's privileges; fixed in 1.8.8 and 2.2.1. Matters for AI-built apps because JSONata is commonly used to let end users or LLM-generated logic write data-transform/query expressions against JSON, so any app that evaluates a user- or model-supplied JSONata expression is directly exploitable, not just apps with untrusted plugin code. [GitHub advisory GHSA-66mm-25pp-rfff](https://github.com/advisories/GHSA-66mm-25pp-rfff)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): treat any expression/template language (JSONata, JMESPath, Handlebars, etc.) evaluated against user- or LLM-controlled input as a code-execution sandbox, not a safe query language — pin to patched versions and never expose it to untrusted expressions without a hardened, audited evaluator.

Matters for AI-built apps because Next.js's built-in `<Image>`/Image Optimization API is enabled by default and processes any image URL an app or its users pass in, so scaffolded apps are exposed without any extra image-handling code being written. [GitHub advisory GHSA-2xp9-vwfh-vxw4](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): recommend pinning Next.js to a patched release and disabling remote/AVIF image optimization when it isn't explicitly needed, since default-on framework features can carry critical RCE risk.
- **Next.js unauthenticated RCE on Windows-hosted servers via path traversal (GHSA-p293-qw3h-jr36, CVE-2026-75604, CVSS 9.0):** Improper path validation (CWE-22) in the Pages/App Router (without Cache Component) lets a remote, unauthenticated request traverse outside restricted directories and achieve full remote code execution specifically when the server filesystem is Windows; affects `next` ≥ 13.4 and < 15.5.24 / ≥ 16.0 and < 16.3.3, fixed in 15.5.24 and 16.3.3, with no workaround for affected Windows deployments. Matters for AI-built apps because agent-scaffolded Next.js apps are sometimes deployed to Windows-based hosts (on-prem, self-managed VMs) where this turns a routine unpatched dependency into complete server compromise. [GitHub advisory GHSA-p293-qw3h-jr36](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): note that Next.js deployments on Windows filesystems need the same urgent-patch treatment as Linux ones — path-traversal bugs can behave differently (and worse) across filesystem semantics.
- **Context7 MCP server prompt injection via unsanitized "Custom AI Instructions" (CVE-2026-75130, CVSS 9.0):** Upstash's widely-installed Context7 MCP documentation server renders a free-text "Custom AI Instructions" field into responses for what looks like a routine library-docs lookup, letting unsanitized attacker-controlled text reach the connected coding agent as if it were trusted context; disclosed impact includes exfiltration of credentials from environment files and destructive file deletion. Affects Context7 ≤ 2.1.2; no public fix or GHSA is documented as of this writing (CWE-1427, credited to Noma Security researcher Eli Ainhorn). Matters for AI-built apps because Context7 is commonly wired into coding agents to fetch up-to-date library docs, so any project depending on it inherits an unpatched, actively-disclosed prompt-injection-to-RCE path with no vendor fix yet. [DigitalApplied: "An MCP Server Bug Scores 9.0. No Fix Is Documented"](https://www.digitalapplied.com/blog/context7-mcp-prompt-injection-cve-2026-75130)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): until a fix ships, treat any MCP server that injects external/free-text content (docs, "custom instructions", scraped pages) into agent context as an untrusted-input channel — sandbox agent file/credential access regardless of which MCP tools are connected, and watch for a Context7 patch release.
- **659 Stripe merchant accounts' live API keys leaked via hardcoded secrets/exposed env files:** A dataset posted to a data-trading forum on 2026-08-18 contained 659 Stripe merchant accounts' live secret keys plus ~35GB of pulled customer/payment data (~688,000 customer records across 42 countries); researchers attribute the source to leaked credentials from infostealer logs, public code repositories, exposed environment files, or poorly protected backups rather than any breach of Stripe itself. Matters for AI-built apps because coding agents routinely read `.env` files and can be prompted into committing them or embedding live keys directly in client/server code, and a single leaked `sk_live_` key gives an attacker direct payment and payout access. [Security Affairs: "50,000 Stripe Secrets Leaked in Public Code"](https://securityaffairs.com/197504/cyber-crime/50000-stripe-secrets-leaked-in-public-code.html)
  - ⚠ PROPOSED RULE UPDATE (chapter 03): add an explicit pre-commit/pre-deploy check that greps for live-looking secret prefixes (e.g. `sk_live_`, `sk_test_` used in prod) and blocks the commit/deploy if found, on top of the existing `.env`/`.git` exposure checks.

### 2026-08-28

- **Chainlit unauthenticated RCE via MCP stdio command injection (GHSA-w3fx-mc44-mf6j, CVE-2026-45018, CVSS 9.8):** When an app enables Chainlit's MCP integration, the `/mcp` endpoint's stdio transport takes a user-controlled `fullCommand` string and only allowlists the executable name, not its arguments, so a request like `npx -y -c 'ARBITRARY COMMAND'` runs shell commands as the Chainlit process with no authentication required; affects `chainlit` ≥ 2.4.0rc0 and ≤ 2.11.1, fixed in 2.12.0 (MCP has been off by default since 2.7.0). Matters for AI-built apps because Chainlit is a popular framework for quickly standing up LLM chat UIs, and any app that turned MCP on inherits unauthenticated RCE with no extra code of its own. [GitHub advisory GHSA-w3fx-mc44-mf6j](https://github.com/Chainlit/chainlit/security/advisories/GHSA-w3fx-mc44-mf6j)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): when exposing an agent/chat framework's MCP or tool-execution endpoint, validate full command lines (not just the executable) and require authentication before any transport (stdio, SSE, HTTP) can register or invoke tools.
- **Chainlit SSRF via unvalidated MCP SSE/streamable-http URLs (GHSA-hvfh-5mj3-5f3j, CVE-2026-45019, CVSS 7.2):** The same `/mcp` endpoint accepts attacker-controlled URLs and headers (including `Authorization`/`Cookie`) for SSE and streamable-http transports with no validation, letting an unauthenticated caller force the Chainlit server to make outbound requests to arbitrary destinations, including internal network services; affects `chainlit` ≥ 2.4.0rc0 and ≤ 2.11.1, fixed in 2.12.0. Matters for AI-built apps because it turns an app's own server into a proxy for internal-network reconnaissance or credential-header replay, from the same MCP feature as the RCE above. [GitHub advisory GHSA-hvfh-5mj3-5f3j](https://github.com/Chainlit/chainlit/security/advisories/GHSA-hvfh-5mj3-5f3j)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): treat any user- or LLM-suppliable outbound URL (webhooks, MCP transports, fetch tools) as a potential SSRF vector and block requests to internal/private address ranges by default.
- **qwed-mcp sandbox-escape bypass of its own RCE fix, still unauthenticated RCE (GHSA-2p69-jpm6-jrxh, CVSS 9.8, no CVE assigned yet):** qwed-mcp's `verify_math_expression` MCP tool passes user-supplied math expressions to a SymPy-based parser guarded by a denylist added in 0.2.1 to fix an earlier `parse_expr()`/`eval()` RCE, but the denylist misses `__getattribute__`/`__call__` and can be evaded by splitting blocked strings across string concatenation, so attacker input can still reach `__globals__` on legitimate SymPy functions (e.g. `sqrt`, `cbrt`) for full arbitrary code execution; affects qwed-mcp ≥ 0.2.1, fixed in 0.2.2. Matters for AI-built apps because qwed-mcp is marketed as a verification/trust layer for agentic AI output, so a project that just patched to "fixed" 0.2.1 is still exploitable, and denylist-based sandboxes around LLM/agent-suppliable expressions are easy to bypass rather than truly closed. [GitHub advisory GHSA-2p69-jpm6-jrxh](https://github.com/QWED-AI/qwed-mcp/security/advisories/GHSA-2p69-jpm6-jrxh)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): reject denylist/blocklist sandboxing of expression evaluators exposed to LLM/agent input (SymPy, JSONata, template languages, etc.) — require an allowlist-based or fully isolated evaluator, since denylists are routinely bypassed even after a patch release.

### 2026-08-31

- **Large-scale study finds LLM agent "skill" marketplaces routinely leak credentials via debug logging:** A large-scale empirical study sampled 17,022 of the ~170,000 skills on SkillsMP (a third-party LLM agent skill marketplace) and found 520 skills (3.1%) carrying 1,708 credential-exposure issues; 73.5% came from ordinary `print`/`console.log` debug statements, because agent frameworks capture stdout into the LLM's context window, making logged secrets retrievable through a plain natural-language query, and 89.6% of the leaked credentials were immediately exploitable without further privilege. Matters for AI-built apps because teams (and coding agents themselves) routinely pull in third-party "skills"/tools with no review, and logging a secret to stdout — an extremely common, easy-to-miss mistake in agent-invoked tool code — is enough to hand it to any user who can chat with the agent. [Wake Forest News: "AI agents are all the rage—but research shows they leak private data"](https://news.wfu.edu/2026/08/26/ai-agents-are-all-the-rage-but-research-shows-they-leak-private-data/)
  - ⚠ PROPOSED RULE UPDATE (chapter 21): warn that agent frameworks commonly capture tool stdout/stderr into LLM context, so any secret written via `print`/`console.log`/debug logging inside agent-invoked tool code is effectively exposed to prompt-based exfiltration — extend the existing logging-redaction guidance (chapter 09) to cover agent-tool stdout, not just structured app logs.

### 2026-09-04

- **"GitSpawn" flaws: CLI coding agents auto-execute repo-controlled Git config commands on startup, across seven agents (Claude Code, OpenAI Codex, Cursor, Grok Build, Goose, Hermes Agent, Qwen Code):** Manifold Security found that these agents gather project context at session start by quietly running `git status`/`git diff`, which lets a malicious repository's own `.git/config` (e.g. via `core.fsmonitor` or similar executable-command config keys) run an attacker-chosen command with the full privileges of the logged-in user, outside the agent's sandbox and with no prompt, approval, or authentication required, just from opening the repo; Claude Code's confirmed path (seen on 2.1.193) was already patched by 2.1.196, and Goose and Cursor also shipped fixes, but Manifold's retest on 2026-09-01 found Hermes Agent, Qwen Code, Grok Build, and a second, separate path in Claude Code still exploitable. Matters for AI-built apps because opening an untrusted or cloned repository with any of these CLI agents can be enough to leak SSH keys, cloud credentials, and API tokens before the developer has typed anything or approved a single action. [cybersecuritynews.com: "GitSpawn Flaws Let Malicious Repositories Execute Code in Claude Code, Codex, Cursor, and Grok"](https://cybersecuritynews.com/gitspawn-flaws-execute-code/)
  - ⚠ PROPOSED RULE UPDATE (chapter 13): warn that CLI agent harnesses commonly run unsandboxed `git` context-gathering commands against a freshly opened/cloned repository before any trust prompt, so a repo's own `.git/config` (fsmonitor, hooksPath, and similar executable-command keys) must be treated as untrusted, attacker-controlled input — never open an unfamiliar repository with an affected agent until it is confirmed patched.

### 2026-09-05
